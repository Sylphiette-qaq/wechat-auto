## Context

`watch` 当前每轮从 WeChat application 根节点调用 `walk_tree`，会访问 Messages 容器内的全部历史行。消息历史越长，远程 D-Bus/AT-SPI 调用越多；HTTP 服务又以约 1 秒频率持续观察，因此完整性和性能之间需要明确偏向性能。

## Goals / Non-Goals

**Goals:**

- 在远程 AT-SPI 访问阶段限制 Messages 列表为末尾固定 10 条直接子项。
- 保留 Chats 容器直接子项、当前会话标题和必要的上层结构，使现有群聊解析契约继续工作。
- 局部结构定位失败时本轮快速结束并记录诊断，不回退全量树扫描。
- 保持 `dump` 全量遍历和现有 HTTP/Go 事件格式不变。

**Non-Goals:**

- 不补扫窗口外历史，不保证短暂出现后滚出窗口的消息一定被发现。
- 不引入缓存、持久化、并发扫描或新的第三方依赖。
- 不改变发送链路的语义；发送回显校验继续使用现有路径。

## Decisions

1. **新增局部扫描器而非改造通用 `walk_tree`。**
   `dump` 需要完整树，发送流程仍依赖通用快照；单独提供 `scan_watch_tree` 可以把 watch 的性能边界表达清楚，避免给诊断模式引入隐式截断。

2. **先遍历上层结构，遇到命名列表后只取直接子项。**
   扫描器对非列表节点按 `max_depth` 深度优先遍历；`Chats` 列表只读取直接行；`Messages` 列表通过 `get_child_count()` 计算起点，仅调用最后 `message_window` 个 `get_child_at_index()`，不再深入消息行子树。

3. **窗口大小默认为 10，并提供正整数 CLI 参数。**
   默认值满足“最新几条”的需求，同时允许容器在真实 UI 验证时用 `--message-window` 调小或调大。非法值在参数入口立即拒绝。

4. **不做全量回退。**
   消息容器未定位、远程对象失效或读取失败时，返回当前已获得的快照或空结果，由现有 `scan_state`/`reason` 诊断处理；性能优先意味着本轮可以漏报。

## Risks / Trade-offs

- [Risk] 新消息行数量少于窗口时，时间区段头可能位于窗口之前，导致部分最新正文缺少时间。 → 仍按现有解析输出，缺少时间的消息使用空区段并依赖去重；不为补时间扩大扫描范围。
- [Risk] 微信 UI 结构变化导致列表名称或层级变化。 → 本轮记录已有结构诊断；`dump` 仍可用于人工排查。
- [Risk] 发送回显仍可能触发全量扫描。 → 本次变更只约束高频 watch；发送是按次调用的低频操作，保持最小改动。

## Migration Plan

1. 部署探针脚本并重启容器，watch 自动使用 10 条窗口。
2. 观察 `scan_state` 中的 `node_count` 与消息事件延迟；必要时通过 `--message-window` 调整。
3. 若需恢复历史诊断，使用 `tree`/`dump`，不修改 watch 性能边界。
